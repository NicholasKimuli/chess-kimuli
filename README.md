# chess.kimuli.me

Step-by-step chess opening lessons, served as a static site from **Cloudflare Pages**.

Pick a side, pick an opening, then walk the main line move by move: the board animates each
move while a card explains the idea behind it and a move list tracks where you are.

- Landing page → **Learn openings as White / as Black**
- Side list → every opening for that side
- Lesson → the board, the annotation, and Prev/Next navigation (arrow keys work too)

---

## URL structure

| URL | Page | Source |
|---|---|---|
| `/` | Landing — choose White or Black | `index.html` (hand-written) |
| `/white/` · `/black/` | Opening list for that side | **generated** by `build.js` |
| `/<side>/<opening>/<variation>/` | The lesson | **generated** by `build.js` |

Live lessons:

- `/white/italian/giuoco-piano/` — Italian Game, Giuoco Piano (White)
- `/black/sicilian/najdorf/` — Sicilian Defence, Najdorf main line (Black)
- `/black/nimzo-indian/rubinstein/` — Nimzo-Indian, Rubinstein main line (Black)

## Repository layout

| File | Role |
|---|---|
| `openings.js` | **The source of truth.** One entry per lesson (metadata + every move). |
| `viewer.html` | Lesson shell (board, annotation card, move list, controls). Used as the route template. |
| `app.js` | Wires the selected opening to the board, controls and keyboard nav. |
| `board.js` | SVG board renderer: positions, animation, highlights, orientation (`BOARD_FLIP`), castling. |
| `style.css` | All styling, including the landing/side-list cards. |
| `index.html` | Landing page. |
| `404.html` | Not-found page. **Required** — without it Pages serves the landing page with a `200` for every unknown URL (soft 404s). |
| `build.js` | Generates `/white/`, `/black/`, the lesson routes, `sitemap.xml`, `robots.txt`. |
| `tools/validate.js` | Data validator. CI runs it before anything is built or deployed. |
| `.github/workflows/deploy.yml` | validate → build → deploy on every push to `main`. |

Generated files are committed (so local previews work) and regenerated by CI, which keeps
them impossible to drift.

## Adding an opening

**Nothing outside `openings.js` needs to change.** The route folder, the side list, the
breadcrumb and the sitemap are all derived from the registry.

### 1. Pick the slugs

A lesson lives at `/<side>/<opening>/<variation>/`:

| Segment | Allowed | Example |
|---|---|---|
| `side` | `white` or `black` | `black` |
| `opening` | lowercase slug, the family | `sicilian` |
| `variation` | lowercase slug, the line | `najdorf` |

→ route `black/sicilian/najdorf`, URL `/black/sicilian/najdorf/`.

Use the real chess names for variations (`giuoco-piano`, `najdorf`, `dragon`, `marshall`) —
they read better in the URL and in the side list.

### 2. Add an entry to `openings.js`

```js
  "sicilian-dragon": {
    key: "sicilian-dragon",                 // registry id, must equal this object's key
    side: "black",                          // "white" | "black"
    opening: "sicilian",                    // URL segment 2
    variation: "dragon",                    // URL segment 3
    route: "black/sicilian/dragon",         // MUST equal `${side}/${opening}/${variation}`
    name: "Sicilian Defence",               // shown as the badge on the side list
    subtitle: "Dragon — Main Line",         // header subtitle; text before " — " is the card title
    line: "1.e4 c5 2.Nf3 d6 3.d4 cxd4 4.Nxd4 Nf6 5.Nc3 g6",  // headline, must match the first moves
    blurb: "One or two sentences pitching the line — shown on the side-list card.",
    intro: "Shown in the annotation card before the first move. <strong>HTML allowed.</strong>",
    boardFlip: true,                        // true for black lessons: board renders from Black's side
    moves: [ /* see step 3 */ ]
  }
```

### 3. Write the moves

Each successive ply (half-move) is one object:

| Field | Type | Notes |
|---|---|---|
| `ply` | number | `1, 2, 3…` in order, no gaps |
| `san` | string | Standard notation as displayed: `e4`, `Nf3`, `exd4`, `Bb4+`, `O-O`, `O-O-O` |
| `from` / `to` | square | Where the piece actually moves: `"e2"` → `"e4"` |
| `piece` | code | `wK wQ wR wB wN wP` / `bK bQ bR bB bN bP` |
| `capture` | code or `null` | The piece standing on `to` (e.g. `"wP"`); must agree with the `x` in `san` |
| `special` | `null` \| `castle-kingside` \| `castle-queenside` | Set only for castling; the rook is moved automatically |
| `title` | string | Card heading — match the repo style: `"5… a6 — The Najdorf Signature"` |
| `explanation` | string | 1–3 sentences on the *idea*, not just what moved. HTML allowed. |

Keep titles in the existing voice (`"11… b5 — Counterattack on the Queenside"`) and explain
the plan for the side being taught.

### 4. Validate, build, preview

```bash
node tools/validate.js     # replays every lesson; exits 1 on any inconsistency
node build.js              # regenerates the side lists, routes, sitemap
python3 -m http.server 8899
# → http://127.0.0.1:8899/  (click through: landing → side → lesson)
```

> Serve over HTTP, not `file://`: page assets use root-absolute paths (`/style.css`) so that
> they resolve from nested routes like `/black/sicilian/najdorf/`.

### 5. Ship it

```bash
git add openings.js white black sitemap.xml
git commit -m "feat: add Sicilian Dragon lesson"
git push            # CI validates, builds, deploys — live in ~30s
```

## What the validator enforces

`tools/validate.js` replays every lesson from the starting position and fails on:

- missing/blank fields, malformed squares, non-slug `opening`/`variation`
- `route` ≠ `side/opening/variation`, duplicate routes, `key` mismatch
- a `ply` out of sequence
- a move whose `piece` isn't actually on its `from` square
- **a move that piece cannot legally make** — wrong knight geometry, a blocked
  bishop/rook/queen path, a pawn moving backwards or two squares from the wrong
  rank, a pawn moving diagonally onto an empty square
- `capture` set without an `x` in the SAN (or vice versa), capturing your own piece
- a piece landing on an occupied square without `capture`
- castling without the right `special`, with the king off e1/e8, with no rook on
  the corner, or with pieces between king and rook
- the headline `line` disagreeing with the lesson's first moves
- a lesson that doesn't end with exactly two kings on the board

Adding a lesson with a typo in a square or a forgotten capture is the normal failure mode —
this catches it before deployment instead of in the browser.

## Deployment

- **Automatic:** pushing to `main` triggers `.github/workflows/deploy.yml`
  (validate → build → stage → `wrangler pages deploy`), ~30s end to end.
  Only the site files are staged; `README.md`, `build.js`, `tools/` and `.gitignore` stay out.
- **Manual trigger:** `gh workflow run deploy.yml --repo NicholasKimuli/chess-kimuli`
- **Manual deploy:** `npx wrangler pages deploy <dir> --project-name chess-kimuli`
- **Secrets:** repo secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID` (if the token is
  rotated, update the secret or deploys will fail).
- Cloudflare Pages canonicalises `.html` URLs: `/viewer.html` 308-redirects to `/viewer`
  (query strings survive). The generated routes don't rely on this.
- **NotFound handling:** Pages serves the root `404.html` for unmatched paths. Keep that file —
  removing it makes every typo'd URL return the landing page with a `200` (soft 404: search
  engines index junk, broken links look healthy).

## Conventions & pitfalls

- **Never change a published `route`** — URLs are the public interface. To rename one, keep the
  old path working (or add a `_redirects` rule) rather than silently breaking links.
- **Black lessons always set `boardFlip: true`** so the board renders from Black's perspective;
  file/rank labels mirror with it.
- **Queenside castling is supported** (`special: "castle-queenside"`) — use it if a line has
  `O-O-O`; the validator will tell you if you forget.
- **`app.js` resolves the opening in this order:** baked-in `window.OPENING_KEY` (generated route
  pages) → `?o=<key>` → the URL path. Unknown openings land on `/`.
- **`openings.js` is evaluated in Node by `build.js` and `tools/validate.js`** — keep it a plain
  `const OPENINGS = { … }` declaration with no DOM access.

## Adding more later

Because everything derives from the registry, the following are all one-entry changes:

- another variation in an existing family (e.g. `/black/sicilian/dragon/`)
- a whole new family for either side (e.g. `/white/ruy-lopez/closed/`)
- a third…nth lesson — the side lists, sitemap and breadcrumbs follow automatically
